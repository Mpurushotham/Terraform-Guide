## DevSecOps Standards for Terraform

These standards establish consistent, secure, and auditable Terraform practices.

### 1. Language, Versioning, and Providers
- Specify Terraform core version and enable dependency lockfiles.

```hcl
terraform {
  required_version = ">= 1.6, < 2.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

- Commit `.terraform.lock.hcl`. Pin providers with version constraints.
- Use provider aliases for multi-account/region; never hardcode credentials.

### 2. Structure and Naming
- Reusable module layout:

```
modules/<module_name>/
  main.tf
  variables.tf
  outputs.tf
  versions.tf
  README.md
  examples/
    basic/
      main.tf
```

- Root stacks by environment:

```
envs/
  prod/
    main.tf
    backend.tf
    terraform.tfvars
  staging/
```

- Naming: use lowercase, hyphenated resource names; include environment and workload.

### 3. State Management
- Use remote state with locking. Example (AWS S3 + DynamoDB):

```hcl
terraform {
  backend "s3" {
    bucket         = "example-tfstate-prod"
    key            = "network/primary.tfstate"
    region         = "us-east-1"
    dynamodb_table = "example-tfstate-locks"
    encrypt        = true
  }
}
```

- Use separate state per environment/workload. Restrict access via IAM least privilege.

### 4. Inputs, Outputs, and Validation
- Validate inputs, provide sane defaults, and avoid sensitive data in outputs.

```hcl
variable "allowed_cidrs" {
  type = list(string)
  validation {
    condition     = alltrue([for c in var.allowed_cidrs : can(cidrhost(c, 0))])
    error_message = "All values must be valid CIDR blocks."
  }
}

output "vpc_id" {
  value       = aws_vpc.this.id
  description = "VPC identifier"
}
```

### 5. Security Baselines
- Default to encryption at rest and in transit.
- No public access by default; require explicit opt-in variables.
- Use KMS-managed keys; rotate regularly.
- Enforce TLS 1.2+; disable weak ciphers.
- Secrets via secret manager (e.g., AWS Secrets Manager or Vault), not variables/TFVARS.

### 6. Linting and Static Analysis
- `terraform fmt -check`, `terraform validate` on every change.
- `tflint` with rulesets; block on errors.
- `tfsec` and `checkov` for IaC security scanning.

### 7. Supply Chain and Reproducibility
- Vendor or pin module sources (git commit SHA or registry version), avoid floating branches.
- Verify module and provider sources. Prefer official or vetted modules.
- Record provenance: use PR templates, changelogs, signed commits where possible.

### 8. Change Management
- Plan files as build artifacts; human review required.
- Apply only from protected branches with approvals.
- Drift detection via scheduled `plan` and notifications.

### 9. Least Privilege IAM
- Split roles: plan-only role and apply role.
- Scoped permissions per workspace/environment.

### 10. Observability and Logging
- Emit module outputs that aid monitoring (e.g., ARNs, IDs).
- Tag all supported resources with ownership, environment, cost center, and data classification.

### 11. Documentation
- Each module must ship `README.md` generated by `terraform-docs`.
- Include example usage in `examples/` that passes `terraform validate`.

### 12. Backups and Recovery
- Enable versioning on state buckets and backup KMS keys.
- Document recovery procedures.
